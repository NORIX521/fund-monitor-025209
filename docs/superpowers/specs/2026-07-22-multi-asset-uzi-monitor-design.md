# 多资产 UZI 研究监控网站设计

日期：2026-07-22
仓库：`NORIX521/fund-monitor-025209`
状态：用户已授权采用推荐方案并自主推进

## 1. 目标

把当前只监控基金 `025209` 的静态页面升级为可批量管理股票、ETF 和公募基金的研究监控台。系统需要持续产出可追溯的评分、风险分层、研究建议、板块新闻以及国内外趋势，同时保留 GitHub Pages + GitHub Actions 的低运维部署方式。

系统不是自动交易工具，不输出保证收益、自动下单或个性化买卖指令。页面中的“建议”统一定义为非个性化研究建议，必须同时展示证据、风险、失效条件、数据时间和置信度。

## 2. 已确认的产品边界

### 2.1 资产范围

- A 股、港股、美股个股：直接进入 UZI 自动评分流程。
- 中国境内公募基金、ETF、LOF：进入基金专用模型；其中可获得持仓的产品，再把主要持仓逐只送入 UZI，汇总为底层持仓质量分。
- UZI 明确不支持直接用个股 65 评委规则评价 ETF、LOF 或基金，因此不会伪造“基金 UZI 直评分”。
- 首版不承诺覆盖海外共同基金、私募基金或无公开净值/持仓的产品；无法识别的输入进入“待确认”队列，不猜测代码。

### 2.2 自动化深度

- 工作日快速任务：更新行情、净值、基金指标、新闻、趋势和已有 UZI 缓存衍生分。
- 新增个股：运行 UZI `lite` 批量评分，保证每个已接受的股票至少有 UZI 自动评分。
- 周末或手动任务：按批次运行 UZI `medium`，更新更完整的股票评分与报告。
- UZI `deep` 需要人工 Agent 介入、逐维证据核查和投资者角色审查，不在无人值守 Actions 中冒充深度结论；未来可作为人工专题报告入口。

## 3. 技术方案比较

### 方案 A：GitHub 原生静态站点（采用）

Pages 提供导入界面；浏览器解析 CSV/粘贴文本并生成预填 GitHub Issue。用户在已登录 GitHub 的页面确认提交后，Actions 校验提交者身份、更新 watchlist、运行数据管道并重新部署。

优点：不新增服务器、不向浏览器暴露令牌、沿用现有仓库和部署链。缺点：导入需要一次 GitHub 确认，结果不是实时返回。

### 方案 B：独立 API 后端（暂不采用）

可实现站内直接提交和实时任务状态，但需要部署、认证、密钥、费用和持续运维。

### 方案 C：纯浏览器本地处理（不采用）

只能保存本地 watchlist，无法真实运行 Python/UZI，也无法形成跨设备、可追溯的自动更新结果。

## 4. 系统架构

```text
Pages 导入中心
  -> 浏览器解析与校验
  -> 预填 GitHub Issue（用户确认提交）
  -> import-watchlist Actions（仅 OWNER/MEMBER/COLLABORATOR）
  -> data/watchlist.json
  -> monitor-and-deploy Actions
      -> 市场/净值/持仓采集
      -> 股票 UZI lite/medium 批处理
      -> 基金专用评分 + 持仓 UZI 加权
      -> 新闻与国内/国际趋势聚合
      -> 数据质量和过期检查
      -> data/dashboard.json + data/assets/*.json
  -> GitHub Pages 部署
```

### 4.1 模块边界

- `scripts/import_watchlist.py`：只负责解析、规范化、去重和安全校验。
- `scripts/providers/`：按市场、基金、新闻来源封装采集；每个 provider 返回统一结果和错误信息。
- `scripts/uzi_adapter.py`：只负责固定版本 UZI 的批量调用、缓存读取、超时和结果规范化。
- `scripts/fund_scoring.py`：只负责基金指标与持仓 UZI 加权，绝不调用个股评委规则评价基金本体。
- `scripts/recommendation.py`：把量化结果映射为研究状态、理由、风险和失效条件。
- `scripts/news_pipeline.py`：聚合、去重、分类和保留来源链接，不生成无来源新闻。
- `scripts/build_dashboard.py`：组装前端所需 JSON；采集器失败时保留最近一次成功数据并标记 stale。
- `assets/app.js`：只负责导入体验、筛选、渲染和本地偏好，不承担金融评分。

## 5. 批量导入体验

### 5.1 支持格式

- 粘贴：每行一个资产，支持 `代码` 或 `代码,名称,类型,备注`。
- CSV：UTF-8/UTF-8 BOM，列名兼容 `code/ticker/代码`、`name/名称`、`type/类型`、`note/备注`。
- 首版单次最多 50 个资产；超过上限时前端和后端都拒绝并给出拆批提示。

### 5.2 规范化

- A 股：`600519` 或 `600519.SH` 规范为 `600519.SH`；深市和北交所按代码段识别。
- 港股：要求 `.HK` 或明确市场，避免与 A 股代码碰撞。
- 美股：大写 ticker，例如 `AAPL`。
- 中国基金：6 位基金代码，类型可写 `fund/基金/etf/lof`；仅靠代码无法无歧义识别时标记待确认。
- 去重键：`market + normalized_code + asset_type`。

### 5.3 GitHub 导入任务

- 页面生成标题前缀 `[watchlist-import]` 和机器可读 JSON 代码块。
- Issue workflow 仅接受仓库所有者或具有协作权限的提交者。
- 解析成功后提交 watchlist，给 Issue 回复导入数量/拒绝项目/运行链接并关闭 Issue。
- 任何未经授权、超过上限、字段非法或含注入内容的 Issue 都不会修改仓库。

## 6. 数据契约

### 6.1 `data/watchlist.json`

```json
{
  "version": 1,
  "updated_at": "ISO-8601",
  "assets": [
    {
      "id": "stock-cn-600519-sh",
      "code": "600519.SH",
      "name": "贵州茅台",
      "asset_type": "stock",
      "market": "CN",
      "note": "",
      "enabled": true
    }
  ]
}
```

### 6.2 `data/dashboard.json`

只保存轻量总览：资产数量、平均分、风险计数、更新时间、各资产摘要和趋势摘要。单资产完整内容拆到 `data/assets/{id}.json`，避免 watchlist 增长后首页 JSON 过大。

### 6.3 单资产记录

每项至少包含：

- 身份：代码、名称、类型、市场、板块。
- 行情/净值：最新值、日期、涨跌、历史序列。
- 评分：综合分、分项分、UZI 版本、模型版本、置信度。
- 研究建议：状态、三条依据、主要风险、失效条件、适用周期。
- 新闻：公司/基金、国内板块、国际板块三组；每条含标题、URL、来源、发布时间、抓取时间和相关度。
- 数据质量：成功来源、失败来源、缓存命中、stale 状态、最后成功时间。

## 7. 评分设计

### 7.1 个股

- UZI 共识与流派分：45%。
- 质量/估值：20%。
- 趋势/动量：15%。
- 风险与杀猪盘信号：15%。
- 新闻与事件冲击：5%。
- 缺失关键维度时降低置信度，不用 0 或默认值冒充真实数据。

首版生产入口不另造第二套股票事实源，而是从本轮成功且已规范化的 UZI 结果映射可验证分项：`overall` 对应 UZI 共识，`fundamental_score` 对应质量/估值，D 技术流派共识对应趋势/动量。独立风险与新闻分在没有同等级结构化字段时保持缺失，权重按现有可用项重算并降低覆盖率；仅有 UZI 总分时进入低覆盖确认状态，不因缺少第二数据源直接判为硬失败。

UZI 固定到经验证的提交 `fce996c33e70eddce8e375f53cd252b549eb3d7c`，版本 `3.9.2`。升级通过单独 PR/提交完成，不在定时任务中静默漂移。

### 7.2 基金/ETF/LOF

- 风险调整后收益：20%。
- 最大回撤与波动：20%。
- 趋势与回撤修复：15%。
- 规模、费率、成立时间、经理任期等稳定性：10%。
- 持仓集中度、风格漂移、行业集中风险：15%。
- 主要持仓 UZI 加权质量分：20%。

若可评分持仓权重覆盖不足 60%，持仓 UZI 分仍显示，但基金综合分置信度降为低；不得把未覆盖部分按 0 分处理。

### 7.3 研究建议

统一状态：

- `优先研究`：分数高、置信度不低且无红线风险。
- `持续观察`：中等分或证据存在明显分歧。
- `等待确认`：数据过期、趋势未确认或关键事件临近。
- `风险偏高`：回撤、波动、估值、集中度或 UZI 风险信号触发。
- `暂不纳入`：识别失败、数据覆盖过低或硬风险触发。

不得输出“保证收益”“必涨”“无脑买入”“自动下单”等内容。建议必须能从当前记录中的数值或新闻来源追溯。

## 8. 新闻和趋势流

- 个股新闻：优先公司公告、交易所/监管披露和有原文链接的公开报道。
- 国内板块趋势：公司/基金板块、产业链、政策和国内供需变化。
- 国际板块趋势：海外同类公司、商品/利率/汇率、供应链和国际政策变化。
- UZI `3_macro`、`7_industry`、`13_policy`、`15_events` 作为股票趋势输入；基金按主要行业与持仓聚合。
- 相同 URL、规范化标题或高度相似标题去重。
- 新闻不生成虚构摘要；自动摘要只允许对已获取正文/摘要做压缩，并保留原链接。
- 没有可靠来源时显示“本周期未获得可靠更新”，不填充常识性套话。

## 9. Actions 设计

### 9.1 `import-watchlist.yml`

- 触发：带固定标题/标签的 Issue 打开。
- 权限：`contents: write`、`issues: write`。
- 身份门：只接受 OWNER/MEMBER/COLLABORATOR；其他关联直接回复拒绝。
- 行为：解析、测试、提交 `data/watchlist.json`，再通过 `workflow_dispatch` 触发监控任务。

### 9.2 `monitor-and-deploy.yml`

- 触发：push、手动、工作日定时。
- 快速任务默认 `UZI_DEPTH=lite`，只处理新增或过期股票；复用缓存。
- 失败时不覆盖最近一次成功数据；任务输出 provider 级错误摘要。
- 数据提交与 Pages 部署在同一 workflow 内，避免由 `GITHUB_TOKEN` 产生的 push 不能再次触发 workflow。

### 9.3 `weekly-uzi-refresh.yml`

- 触发：周末或手动。
- 默认 `medium`，每批最多 10 个股票；批次失败互不覆盖。
- 单 job 设置小于 GitHub-hosted runner 6 小时上限的超时；缓存 UZI 依赖和有效中间结果。
- 完成后触发统一 dashboard 构建和 Pages 部署。

## 10. 前端信息架构

### 10.1 总览

- 监控资产数、平均综合分、高风险数、过期数据数。
- 市场/类型/板块筛选和搜索。
- 国内趋势、国际趋势和近期高影响事件摘要。

### 10.2 资产列表

- 代码/名称、类型、最新值、日变化、综合分、研究状态、置信度、更新时间。
- 支持按分数、风险、更新时间排序。

### 10.3 资产详情

- 分项评分条和 UZI/基金模型来源。
- 净值或价格历史。
- 研究建议、证据、风险、失效条件。
- 国内新闻、国际新闻和板块趋势，全部可打开原文。
- 数据质量与运行状态。

### 10.4 导入中心

- 粘贴与 CSV 两种入口。
- 导入前预览：有效、重复、待确认、拒绝。
- 生成 GitHub 导入任务按钮和模板下载。

视觉上延续现有深色研究面板，保留绿色/蓝色为信息与正向状态、黄色为待确认、红色为风险。桌面宽度上限 1440px；390px 移动端使用单列卡片、底部筛选和不小于 44px 的触控目标。

## 11. 容错、安全与合规

- 所有用户输入做长度、字符、字段和数量白名单校验；HTML 渲染统一转义。
- 不在前端或仓库保存 GitHub PAT、数据源密钥或个人交易信息。
- UZI/数据源超时按资产隔离；保留上次成功数据并显示 stale。
- 每个分数保存模型版本、输入时间和覆盖率，支持追溯。
- 基金披露持仓明确标记报告期，不表述为实时仓位。
- 新闻与投资研究结果均展示“仅供研究，不构成投资建议”。

## 12. 测试和验收

### 自动测试

- Python：导入解析、市场识别、去重、基金评分、持仓加权、UZI 结果映射、新闻去重、stale 回退和 JSON schema。
- JavaScript：CSV/粘贴解析、HTML 转义、筛选排序和数据缺失渲染。
- 静态检查：Python 编译、JS 语法、JSON/YAML 解析、敏感信息扫描。
- 工作流：导入者身份门、超过 50 项拒绝、非法 Issue 不写入。

### 端到端验收

- 至少导入 2 只股票、1 只基金和 1 只 ETF 的混合集合。
- 所有股票有 UZI 自动评分或明确失败原因；基金有专用评分并显示持仓 UZI 覆盖率。
- 每项资产都有研究状态、依据、风险、失效条件和数据时间。
- 有来源时展示国内/国际趋势新闻及原链接；无来源时明确为空。
- Actions build/deploy 成功；Pages 主页和关键 JSON 返回 HTTP 200。
- 1440px 桌面和 390px 移动端完成交互与视觉检查，无控制台错误。

## 13. 首版交付与后续

首版直接在现有仓库内替换单基金首页，但保留 `025209` 作为默认 watchlist 样例。优先交付可运行的导入、数据契约、评分、新闻、Actions 和多资产 UI；完整 UZI medium 批次若受外部数据源影响，应显示真实失败状态，不以假数据阻塞网站其余资产更新。

后续可选增强：独立后端实现站内直接提交、用户账户、多 watchlist、邮件/微信通知、人工 UZI deep 专题报告和历史评分回测。
